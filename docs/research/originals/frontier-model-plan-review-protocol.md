# **Verification of Autonomous Pre-Implementation Plans: Architectural Review Protocols for Asymmetric Model Orchestration**

In fully autonomous software engineering pipelines where a local, resource-constrained model authors an implementation plan and a frontier model acts as an automated quality gate, the pre-implementation verification phase is the primary determinant of system success. Verifying software architecture and task decomposition prior to code synthesis isolates structural defects when they are least expensive to rectify. When Claude Opus reviews a plan generated by a local Qwen 3.x-class model without human oversight, the system must be governed by rigorous defect-containment protocols, mathematically grounded context constraints, and deterministic verdict schemas.

## **Empirical Value and Defect Removal Dynamics of Early Plan Verification**

Formal software engineering literature and modern empirical evaluations of autonomous language model agents establish that catching defects during the planning phase yields substantial efficiency and quality advantages over downstream code review.

### **Defect Distribution and Verification Dynamics in LLM Agents**

The structural vulnerabilities documented in human software development are amplified in autonomous agent pipelines. Evaluations of repository-level software development benchmarks, such as E2EDevBench, reveal that autonomous agents fail far more frequently during requirement comprehension and multi-step architectural planning than during localized code synthesis9.  
Systematic root-cause taxonomies of multi-agent software engineering workflows categorize agent failures across three stages9:

* **Task Planning Failures (55.8%):** Omissions of core specification requirements account for 27.9% of failures, structural misinterpretations of the domain problem cause 22.2%, and architectural anti-patterns contribute 5.6%9.  
* **Task Execution Failures (38.6%):** Unresolved dependency ordering accounts for 21.0% of failures, shallow or partial implementations represent 12.5%, context loss constitutes 1.9%, and fundamental model synthesis errors account for 3.2%9.  
* **Task Verification Failures (5.7%):** Defective self-tests and misconfigured validation commands fail to expose regressions9.

In decoupled plan-then-execute architectures, downstream code synthesis is strictly bounded by plan validity10. When an autonomous executor operates from an unverified or flawed plan, downstream implementation drifts into localized, superficial patches that may pass naive test assertions while violating core system contracts9. Post-hoc code review becomes ineffective once this drift occurs; empirical code review studies demonstrate that human and model defect detection drops toward zero when diff sizes exceed 400 lines of code12. In unconstrained agent refactoring tasks, sycophantic compliance causes code churn to explode to 8 to 30 times the size of the original codebase, overwhelming downstream context windows with non-essential changes13.  
Pre-execution plan verification provides an effective intervention. Enforcing a formal plan-verification gate eliminates cognitive drift and structural omissions prior to code synthesis, yielding relative resolution improvements between 7.47% and 39.95% on repository-level software benchmarks14.

## **Plan Review Taxonomy and Frontier Model Evaluation Efficacy**

To verify an implementation plan authored by a local model such as a Qwen 3.x-class model, the frontier reviewer must evaluate the artifact across six orthogonal dimensions. Empirical evaluations of frontier models on unimplemented software specifications demonstrate high proficiency in high-level invariant checking alongside distinct blind spots in low-level verification mechanics16.

### **Essential Evaluation Dimensions**

A comprehensive implementation plan review requires auditing the specification against six structural criteria:

* **Decomposition:** The macro objective must be partitioned into cohesive, decoupled tasks adhering to strict single-responsibility boundaries, preventing the interweaving of unrelated concerns such as mixing schema migrations with presentation-layer adjustments.  
* **Ordering and Dependencies:** The plan must demonstrate a valid topological sort across all steps, ensuring that database migrations, data transfer objects, core abstractions, and prerequisite API endpoints are implemented and staged prior to dependent downstream consumers.  
* **Verifiability of Validation Checks:** Each task must declare an executable, deterministic check command (such as targeted unit tests, linters, or schema validation scripts) that provably fails on the unamended codebase and succeeds only upon correct task fulfillment.  
* **Task Granularity and Scope:** Tasks must be sized to remain within the reliable execution envelope of the local executor model, constraining code modifications to approximately 50 to 150 lines of churn across no more than two or three files per step.  
* **Codebase Consistency:** Proposed naming patterns, architectural idioms, directory structures, and third-party library imports must align strictly with existing repository conventions, preventing package hallucinations and diverging structural idioms.  
* **Risk Areas and Invariant Preservation:** The review must audit subtle failure points, including network timeouts, idempotency constraints, race conditions, memory leaks, error-handling cascades, and edge-case operational boundaries.

### **Frontier Reliability and Systematic Blind Spots**

Rigorous comparative evaluations across 12 frontier models reviewing unimplemented software plans reveal marked divergences in review fidelity16. Models such as Claude Opus and Tencent Hunyuan 3 demonstrate exceptional precision when identifying missing environmental contracts, concurrency hazards, and protocol violations16. In asynchronous message-handling pipelines, for instance, Claude Opus consistently identifies call-site timeout omissions where extended wait thresholds turn upstream delivery retries into silent acknowledgments that violate at-least-once processing guarantees16. Similarly, frontier models reliably detect ordering defects, such as executing rate-limiting operations before deduplication checks, which permits duplicate payloads arriving after limit exhaustion to escape processing gates16.  
Conversely, frontier models exhibit a major blind spot regarding check verifiability: auditing whether a proposed check command will actually exercise the targeted change16. In controlled empirical benchmarks containing an invalid test that was pointed at the wrong module—making it physically impossible for the test to catch the underlying regression—11 out of 12 frontier models (including Claude Opus and OpenAI Codex) rubber-stamped the validation command without flagging the defect16. Tencent Hunyuan 3 was the sole model to catch the targeting discrepancy16.  
Furthermore, frontier models frequently stumble over code search artifacts: when an integrated grep or file-globbing tool returns an empty result due to slight path mismatches, the reviewer model often hallucinates that the underlying file does not exist, generating false-positive blocking critiques16. Benchmark analyses in CriticBench confirm this vulnerability: LLMs achieve significantly lower F1 scores when evaluating fine-grained algorithmic and execution-trace correctness than when reviewing high-level logic17.

## **Context Engineering and Input Representation Trade-Offs**

Determining what repository information to supply to Claude Opus requires balancing structural awareness against token overhead and context degradation. Supplying insufficient repository context produces hallucinated critiques, whereas supplying excessive context degrades model attention and escalates token costs19.

### **Context Ingestion Modalities**

The input configuration supplied to the frontier reviewer fundamentally dictates review accuracy, operational cost, and false-positive rates:  
Providing the plan alone is computationally inexpensive, requiring only 2,000 to 5,000 tokens per evaluation19. However, this configuration deprives the reviewer of codebase context. The reviewer cannot verify whether referenced classes exist, whether method signatures match, or whether proposed file locations conform to existing module boundaries21. Consequently, defect recall remains low (\~25%), and the reviewer frequently hallucinates APIs or flags false inconsistencies16.  
Augmenting the plan with an Abstract Syntax Tree (AST) repository map—similar to the tree-sitter architecture employed by Aider—provides the reviewer with a dense, structured overview of all declared classes, methods, and function signatures across the repository within an efficient footprint of 1,000 to 4,000 tokens19. This structural view elevates defect recall to approximately 65%, allowing the model to spot missing symbols, invalid types, and broken interface dependencies across module boundaries without ingesting raw file contents21.  
The optimal operating frontier combines the plan, the AST repository map, and the full source text of targeted files explicitly referenced in the plan's milestones16. By budgeting between 15,000 and 40,000 tokens, this hybrid context allows the model to ground its review in exact method implementations and edge-case logic within affected modules, while maintaining broad structural awareness of the wider codebase via the AST map16. This configuration achieves defect detection recall rates of 88% to 92% and minimizes false positives by anchoring assertions in concrete source code16.  
Conversely, dumping an entire codebase into an extended context window (between 200,000 and 800,000 tokens) introduces substantial operational inefficiencies19. Although frontier architectures support large context windows, empirical evaluations show that model effectiveness degrades at an estimated rate of 2% per 100,000 tokens of accumulated context due to attention dilution19. Furthermore, this triggers the "Lost in the Middle" phenomenon: when critical architectural evidence is located in the interior of a long prompt context, retrieval accuracy falls from 75.8% to 53.8%20. Monolithic context ingestion also inflates per-review API costs from under \$1.50 to between \$15.00 and \$25.00 per pass, while degrading overall defect recall to 55%–65%19.

| **Plan Alone** | 2,000 – 5,000 tokens | \$0.05 – \$0.10 | \~25% (Detects only generic logic flaws) | High (Hallucinates non-existent codebase APIs) |
| **Plan \+ AST Repo Map** | 4,000 – 10,000 tokens19 | \$0.15 – \$0.30 | \~65% (Catches signature & type mismatches)21 | Moderate (Lacks internal method semantics) |

| **Monolithic Codebase Dump** | 200,000 – 800,000 tokens19 | \$6.00 – \$24.00+19 | \~55%–65% (Degraded by attention dilution)19 | Moderate-High (Lost-in-the-middle degradation)20 |

### **The Sandboxed Read-Only Reviewer Perimeter**

Autonomous reviewer agents require a strictly isolated execution environment16. In agent harness benchmarks, when a reviewer model is provisioned with write or execution tools, it frequently attempts to write patches itself rather than providing a structured plan critique16.  
To maintain review integrity, the harness must construct a sandboxed environment around Claude Opus following established isolation patterns16:

* Allowed operational tools must be restricted to read-only capabilities: file reading, directory listing, regex search, and glob matching16.  
* Modification tools must be denied: file creation, file editing, bash shell execution, web fetching, and git mutation commands16.  
* At the OS level, process lifecycles must be managed using explicit process-tree termination hooks to prevent orphaned processes from leaking pseudo-terminal file descriptors (/dev/ptmx), which can exhaust system limits and stall automated background pipelines16.

## **Typed Verdict Protocols and Cross-Model Revision Dynamics**

Unmoderated natural-language dialogues between disparate language models tend to diverge without strict structural constraints. Interaction between Claude Opus and a local Qwen 3.x model must be governed by typed schemas and a clear understanding of how smaller open-weight models process critique.

### **The Separation Principle and Binding Verdict Architecture**

The frontier model must not possess unconstrained authority to alter environment states directly. Following formal agent design principles, the architecture must maintain a separation between proposing an assessment and determining whether that assessment satisfies system criteria24. The language model generates candidate findings; a deterministic software harness evaluates those findings and computes the binding verdict24. The terminal verdict of APPROVE is computed by the harness if and only if zero blocking findings are registered24.  
The reviewer is restricted to emitting two primary verdict categories:

* **APPROVE:** The plan satisfies all architectural invariants, decomposition constraints, and validation criteria. The harness locks the plan artifact, provisions execution branches, and transitions the pipeline to task execution.  
* **REVISE:** The plan violates specific structural criteria. The harness captures the structured findings, updates its state machine, and routes localized feedback back to the local model.

### **Preventing Plan Rewriting**

When a frontier model identifies defects in an implementation plan, its default tendency is to rewrite the plan entirely. This behavior introduces two failure modes:

* **Context Misalignment for the Executor:** The weaker local model authored the original plan within its own attention budget and functional representations. If the frontier model replaces the artifact with an entirely new document, it often introduces unfamiliar design patterns and terminology that confuse the weaker executor during subsequent code generation.  
* **Review Instability and Non-Convergence:** Whole-document plan regeneration forces the reviewer on subsequent passes to evaluate completely new text, eliminating the stability required for convergence.

To prevent plan rewriting, the orchestrator enforces an output schema that permits only diagnostic findings and strictly forbids outputting a replacement plan25. System prompts must explicitly instruct the reviewer: *"You are an auditor, not an author. You are strictly forbidden from outputting an amended plan. You must only emit structured defect findings targeting specific tasks."*

### **Asymmetric Model Execution and Critique Absorption**

Empirical research into language model self-correction highlights sharp performance divides based on parameter scale. Smaller models cannot reliably execute open-ended self-refinement; single-pass outputs frequently match or exceed multi-turn conversational corrections when feedback is qualitative or broad (paired McNemar significance test ![][image9])27. When presented with broad qualitative feedback—such as an instruction to improve the modularity or error handling of a task—a Qwen 3.x-class model suffers from attention drift15. In attempting to address open-ended suggestions, it often alters functional elements that were already correct, hallucinates helper utilities, or introduces syntactic regressions15.  
Conversely, smaller models excel when provided with localized, atomic, criterion-referenced corrections15. When feedback specifies the exact target task ID, the conflicting file path, and an explicit invariance condition, weaker models successfully correct their output in up to 39.95% of previously failed attempts15. Constraining the revision target allows the smaller model to focus its attention on resolving the specific contradiction without disturbing the surrounding plan structure15.

| Feedback Modality | Executor Processing Mechanism | Execution Impact on Qwen 3.x Plan Revision | Revision Convergence Rate |
| :---- | :---- | :---- | :---- |
| **Global Qualitative Feedback** *(e.g., "Refactor task 2 for better modularity")* | Diffuse attention across full plan; attempts multi-variable optimization simultaneously | Attention drift; modifies previously correct tasks; injects hallucinated utilities15 | **Low** (McNemar test ![][image9]; no aggregate gain over single-pass)27 |
| **Atomic Criterion-Referenced Feedback** *(e.g., Target ID, file path, invariant)* | Bounded attention on explicit task block; localized constraint satisfaction15 | Deterministic correction; updates only the failing check command or dependency edge15 | **High** (Resolves up to 39.95% of previously failed tasks)15 |

### **Differential Re-Review Protocol**

To maintain token efficiency and prevent revision cycles from diverging, the orchestrator implements differential re-review29. When Qwen revises its plan, the model is instructed to emit only an amended patch block containing the specific modified task structures, mapped to their corresponding finding\_id29. The orchestrator then re-invokes Claude Opus, passing solely the original findings report, the git diff of the amended task sections, and relevant file contexts29. Claude Opus audits the diff in isolation to verify that the required invariance criteria have been satisfied without reopening settled plan sections, halting review scope creep and guaranteeing pipeline convergence29.

## **Frontier Reviewer Failure Modes and Prompt Mitigations**

Deploying a frontier model as an unassisted quality gate introduces systemic failure modes rooted in transformer alignment properties and attention dynamics.

### **Anchoring Bias on Weak Model Framing**

Large language models exhibit significant anchoring bias: when presented with a preliminary draft, models bias their reasoning toward that initial frame, adjusting insufficiently from it30. Empirical studies benchmarking anchoring effects across model scales show that larger, highly aligned frontier models are paradoxically *more* susceptible to context anchoring than smaller models31. A smaller model generates higher variance outputs, whereas a frontier model follows prompt premises closely31.  
In implementation plan review, if Qwen presents an architectural plan based on a flawed premise—such as implementing client-side polling instead of leveraging an existing WebSocket interface—Opus exhibits a strong tendency to anchor on Qwen’s framing. Rather than rejecting the approach and mandating the WebSocket architecture, Opus often focuses on optimizing the polling interval.  
To mitigate this bias, the orchestrator enforces an invariant-first, two-stage evaluation protocol30. Prior to reading Qwen’s tasks, Opus must read the user issue and the repository map and write an independent set of architectural invariants and mandatory interface touches. The prompt then instructs: *"Compare the proposed plan against your independently derived invariants. If the plan violates these core architectural pathways, reject the plan structure entirely."*

### **Rubber-Stamping and Sycophancy**

Reinforcement Learning from Human Feedback (RLHF) optimizes models toward conversational politeness and compliance, which often manifests as sycophancy—the tendency to agree with user-submitted assumptions and validate flawed proposals to avoid perceived conflict32. Mechanistic analysis demonstrates that sycophantic alignment emerges in the deeper transformer layers, where user-stated opinions structurally override learned factual knowledge34.  
In plan review, sycophancy leads to rubber-stamping: the frontier model skims the plan, assesses that the prose appears orderly, and issues an APPROVE verdict with conversational praise, completely missing missing timeouts, duplicate checks, or incorrect check assertions16.  
To prevent rubber-stamping, the reviewer must be stripped of polite conversational personas and assigned an adversarial inspection role16. The system prompt enforces an explicit falsification mandate:

* The model is instructed to assume the plan contains at least one critical race condition, circular dependency, or unverified assumption16.  
* For every check command proposed, the reviewer must identify a condition under which the check would pass despite the underlying feature being broken; if it cannot prove the check command fails on current code, the check must be flagged as unverified16.  
* Conversational preambles, praise, and discursive sign-offs are strictly prohibited, with output restricted to the structured JSON schema25.

### **Over-Specification and Capability Mismatch**

Frontier models often fail in the opposite direction by demanding abstraction patterns that exceed the executor's operational capacity. Claude Opus may demand enterprise architectural patterns—such as dynamic dependency injection containers, generic repository wrappers, and deep visitor abstractions—that require broad contextual awareness to coordinate across multiple files.  
A local Qwen 3.x coding model excels at localized, imperative tasks, but its execution degrades when navigating distributed abstractions across numerous files38. Over-specified architectural demands cause the local executor to generate excessive boilerplate, misconfigure generic types, and deplete its context window, inducing cascading failure13.  
To mitigate capability mismatch, the review prompt must explicitly define the local model's operational envelope:

EXECUTOR SPECIFICATION:  
The executor is a local 30B-tier model (Qwen 3.x-Coder).  
It operates with high precision on localized, concrete, imperative code modifications.  
It fails on complex meta-programming, dynamic class generation, and deep inheritance hierarchies.

CONSTRAINTS ON FINDINGS:  
1\. Do not require abstract design patterns where a direct, concrete function suffices.  
2\. Ensure no single task requires editing more than 3 distinct files or exceeds 150 lines of churn.  
3\. Every required fix criterion must be expressible as a concrete, imperative instruction.

The workflow operates across five distinct phases:  
In the plan generation phase, the local Qwen 3.x model parses the requirement specification and generates a structured implementation plan defining milestones, target file paths, topological dependencies, and check commands.  
In the context ingestion and sandboxing phase, the deterministic harness parses the declared file paths from the plan. It executes a tree-sitter extraction to build an AST symbol map of the repository, loads the targeted source files into memory, and provisions a strictly read-only execution perimeter around Claude Opus, granting access to search tools while blocking modification and execution tools16.  
In the adversarial audit phase, Claude Opus executes a two-stage evaluation. It first establishes core architectural invariants independently from the user issue and AST map, and then audits Qwen's plan against those invariants30. The model applies an adversarial falsification mandate across the six review dimensions, auditing check commands to ensure they target the actual defect sites16. The output is strictly formatted as a structured report conforming to the JSON schema, prohibiting unsolicited plan rewrites25.  
In the deterministic verdict gate, the harness parses the JSON report and computes the binding verdict24. If zero blocking findings are registered, the harness issues an APPROVE verdict, locks the plan artifact, and transitions the pipeline to code generation.  
If blocking findings exist, the harness emits a REVISE verdict and triggers the differential remediation loop24. The orchestrator extracts the atomic findings—specifying target task IDs, file evidence, and invariance criteria—and injects them into Qwen's prompt context15. Qwen regenerates only the affected task blocks as a unified diff. The harness then feeds this localized patch back to Claude Opus for a differential re-review, bounding the token footprint and preventing cognitive drift until the plan achieves deterministic approval29.

## **Nuanced Conclusions and Actionable Recommendations**

Implementing an unassisted, two-model plan review pipeline requires recognizing that the primary vulnerability in autonomous code generation lies in upstream task formulation rather than syntax synthesis. Catching structural defects prior to execution avoids compounding code churn and attention degradation.  
To operationalize this review framework successfully, system implementations should adhere to four engineering practices:  
First, maintain strict context boundaries by providing the reviewer with an AST repository map and targeted source files, avoiding monolithic repository dumps that trigger attention degradation and inflated token expenditure19.  
Second, enforce an invariant-first review sequence within the frontier model's instructions to mitigate anchoring bias, requiring the reviewer to independently derive necessary system contracts before auditing the candidate plan30.  
Third, constrain the reviewer's output to an atomic findings schema that disallows whole-document plan rewriting, ensuring that revisions remain localized and within the instruction-following capabilities of smaller executor models15.  
Finally, restrict the reviewer's execution environment to read-only search primitives, reserving terminal verdict authority for a deterministic software harness that gates execution based on verified finding counts16.
