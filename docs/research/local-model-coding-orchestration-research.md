# Empirical Evaluation and Architectural Design of Heterogeneous Agentic Coding Systems: Local Open-Weight Orchestration with Sparse Frontier Model Escalation
The conventional paradigm of deploying monolithic commercial frontier models across every stage of agentic software engineering is economically unsustainable for repository-scale development[^1]. Autonomous problem resolution on benchmarks such as SWE-bench Pro and SWE-bench Verified routinely requires dozens of interactive turns, extensive terminal output ingestion, and repeated environment probes[^3]. When an expensive frontier model—such as Claude Opus 4.8 or GPT-5—is deployed end-to-end as both terminal operator and patch author, cumulative context accumulation elevates inference expenses to \$18.00–\$40.00 per resolved task[^2].  
A compelling architectural alternative distributes cognitive responsibilities across a heterogeneous hierarchy. In this configuration, an efficient open-weight model—such as a 30B-parameter Qwen 3.x-class model deployed on a single local GPU—serves as the primary operational agent and local coordinator, performing repository indexing, issue localization, and initial patch synthesis[^3]. Commercial frontier application programming interfaces (APIs), including the Claude 3.5 and 4.x tiers, are invoked selectively as specialized consultants or fallbacks only when the local agent encounters rigorous failure boundaries[^3]. Recent empirical research validates that this hybrid division of labor matches or exceeds the quality of continuous frontier-model execution while reducing operating costs by 60% to 70%[^1]. Achieving these efficiencies with an uncalibrated, purely prompted local orchestrator requires addressing distinct behavioral pathologies, context degradation limits, and interface mismatches through external architectural scaffolding[^5].

## Empirical Studies on Small-Model Orchestration and Hierarchical Cascades
The empirical literature investigating heterogeneous model collaboration in complex reasoning and software development encompasses four primary architectural archetypes: end-to-end reinforcement-learning controllers, staged pipeline divisions, worker-advisor review hierarchies, and formal optimization cascades.  
The first archetype trains a compact network specifically to govern tool sequencing and model dispatch. NVIDIA Research developed ToolOrchestra to train Nemotron-Orchestrator-8B, an 8-billion-parameter controller initialized from Qwen3-8B[^7]. Rather than executing all subtasks internally or delegating indiscriminately, the orchestrator was trained via Group Relative Policy Optimization (GRPO) over multi-turn trajectories to optimize a joint objective comprising task correctness, token compute expenditure, execution latency, and adherence to user tool preferences[^9]. Evaluated on the text split of Humanity's Last Exam (HLE), FRAMES, and $\tau^2$-Bench, Orchestrator-8B coordinated a heterogeneous pool of domain tools alongside specialized open models (such as Qwen2.5-Coder-32B) and frontier foundation models (GPT-5)[^9]. On HLE, Orchestrator-8B achieved an accuracy of 37.1%, surpassing monolithic GPT-5 (35.1%) while running 2.5 times faster and operating at approximately 30% of the financial cost[^1]. The model called the flagship frontier model in only ~40% of interaction steps, relying on local compute or lightweight tools for the remainder of the trajectory[^12].  
The second archetype decouples the software engineering workflow into discrete functional stages, assigning models according to operational intensity. AI21 Labs demonstrated this paradigm on the full 731-task public set of SWE-bench Pro[^3]. Software issue resolution exhibits an asymmetry between repository exploration (which consumes vast context tokens locating files and reproducing bugs) and code modification (which requires inductive synthesis across modules)[^3]. AI21 deployed an open-weight model (MiniMax-M3) to execute parallel exploratory rollouts within containerized Docker environments[^3]. These rollouts mapped code dependencies and authored reproducer scripts, achieving ~90% coverage of the code lines touched by gold patches[^3]. A intermediate model (GPT-5.2) extracted and consolidated this discriminative context into a structured brief, after which a single frontier generation (using Claude Opus 4.8 or Fable 5\) authored the final patch[^3]. This explore-and-patch architecture attained an 80.8% resolve rate on SWE-bench Pro at an average expenditure of \$5.99 per task, outperforming a solo Claude Opus 4.8 agent (which cost \$18.28 per task) while reducing token expenditures by 67.2%[^3].  
The third archetype establishes a worker-advisor hierarchy. Fireworks AI formalized this structure to eliminate the context overhead of multi-turn frontier execution[^6]. In this framework, an open-source worker model (GLM-5.2 or Kimi-K2.6) served as the operational "hands," executing all terminal commands, code modifications, and local unit test runs[^6]. A commercial frontier model (Claude Opus 4.8) served as a read-only advisor with no terminal access[^6]. Once the worker completed initial edits, it submitted an audit request comprising the candidate git diff and execution trace to the advisor, which scored the changes against strict verification categories[^6]. On a 60-task stratified subset of SWE-bench Pro, adding a single advisor review call to GLM-5.2 raised the resolve rate from 59% to 66% while maintaining an average cost of \$6.09 per task, compared to \$18.28 for end-to-end Opus 4.8 execution[^6]. On Terminal-Bench 2.1, GLM-5.2 paired with the Opus advisor matched solo Opus 4.8 performance (80% resolve rate) at roughly half the total cost (\$3.50 versus \$6.61)[^6]. Fireworks AI reported that introducing an initial planning call prior to execution doubled advisor expenditure without improving downstream patch quality, establishing a single terminal review as the optimal design[^6].  
The fourth archetype applies formal statistical optimization and trajectory monitoring to dynamic routing. Son et al. introduced SWE-Router at the ICML 2026 DL4Code Workshop, demonstrating that prompt-only routers face an information-theoretic Bayes-error floor because software issue descriptions do not expose whether a bug requires a single-line fix or a multi-file architectural refactor[^8]. SWE-Router implements value-based temporal routing: an open-weight worker executes several exploratory turns to gather directory structures and failure traces, after which a learned value head evaluates the partial trajectory to determine whether the weak model will succeed[^8]. If the success probability falls below a cost-calibrated threshold, execution transitions to a frontier model[^8]. Dekoninck, Baader, and Vechev unified sequential cascading and prompt routing into Cascade Routing (ICML 2025), framing model selection as a linear programming optimization that achieved over 10% performance improvements on SWE-bench and LiveCodeBench while deferring to larger models on only 30% to 50% of queries[^17]. Similarly, the ORACLE framework demonstrated that online, adaptive verifier feedback loops lift the Pareto frontier by up to 7 percentage points over static routing baselines on SWE-bench and Terminal-Bench 2.0[^21].

## Efficacy and Failure Modes of Purely Prompted Open-Weight Orchestrators
While specialized models trained with reinforcement learning exhibit balanced multi-model scheduling, empirical evidence demonstrates that **the hypothesis fails when open-weight models (such as Qwen 2.5/3, GLM, or DeepSeek) are relied upon as purely prompted, unconstrained orchestrators**[^10]. When an open-weight model is instructed via natural language prompts to assess task complexity, manage subtask dispatch, and invoke frontier APIs autonomously, it exhibits severe behavioral and cognitive failure modes[^10].  
The most prominent barrier is the manifestation of systematic routing biases[^10]. In the pilot investigations documented in the ToolOrchestra study, off-the-shelf open models (including Qwen3-8B and Qwen3-32B) were prompted with full descriptions of candidate models alongside explicit cost-minimization instructions[^10]. When tasked with solving heterogeneous problems, the prompted Qwen models delegated **73% of all decisions to the frontier model (GPT-5)**, effectively operating as pass-through proxies and negating any cost benefit[^10]. The authors formalized this behavior as *other-enhancement bias*—an inability of prompted models to calibrate their own operational competency against external capabilities under cost constraints[^10]. Conversely, proprietary frontier models prompted to act as routers exhibit *self-enhancement bias*; GPT-5 routed 98% of queries to itself or its family variants, disregarding more economical open alternatives[^10].  
Beyond routing biases, software engineering environments introduce five specific operational failure modes when open-weight models act as prompted orchestrators:  
Over-delegation occurs when the orchestrator defers trivial, deterministic operations to the expensive frontier model[^11]. In unconstrained settings, prompted models frequently construct API calls to frontier endpoints simply to format grep patterns, inspect file system directories, or parse standard compiler outputs, incurring substantial network round-trip latency and commercial token charges for tasks that local rule-based scripts execute instantaneously[^35].  
Under-delegation and patch thrashing represent the inverse failure mode[^4]. When an open-weight model encounters a complex logic flaw or an ambiguous runtime regression, it routinely fails to recognize its own cognitive limitation[^4]. Instead of escalating to a frontier model, the agent becomes trapped in cyclic debugging loops, modifying identical code blocks across consecutive turns, alternating between equivalent failing implementations, and exhausting its execution budget without making progress[^4].  
Decomposition collapse and premature completion emerge from the orchestrator's inability to maintain hierarchical execution integrity[^11]. When presented with a multi-file objective, prompted 30B-scale models often formulate high-level task plans but collapse during execution[^11]. The model frequently interprets the successful completion of an initial exploratory step (such as locating a class definition) as resolving the overarching problem, terminating the workflow prematurely and reporting false success without executing the required modifications or tests[^11].  
Tool-calling syntax drift and schema degradation intensify over extended trajectories[^11]. While top-tier open models exhibit high JSON compliance on single-turn benchmarks, their adherence degrades under multi-turn conversational load[^11]. As context history accumulates, the orchestrator begins omitting required schema fields, mixing natural language reasoning directly into structured JSON payloads, or hallucinating non-existent function arguments, which triggers execution halts in automated harnesses[^11].  
Context rot and state amnesia degrade reasoning over extended token spans[^5]. As the conversational history expands with bash command logs, raw stack traces, and multi-file listings, the model suffers from the "lost-in-the-middle" phenomenon[^39]. It loses access to instructions provided in the initial issue description, forgets constraints identified during early exploration, and introduces regressions into previously passing modules[^4].  
Consequently, a local 30B model cannot function as an unconstrained, free-form orchestrator[^10]. It can, however, serve effectively as an *operational worker within an externally enforced, deterministic control scaffold*[^6].

## Escalation Signals: Evaluating Mechanisms for Predicting Failure
Designing an autonomous escalation policy requires identifying signals that reliably indicate that the local model cannot resolve the current task[^8]. Relying on the model to verbally assess its own performance is ineffective; LLMs display pronounced sycophancy and automation bias, routinely asserting complete confidence in invalid or non-compiling code[^11]. Effective escalation mechanisms depend instead on deterministic verifiers, learned trajectory representations, and state churn metrics[^4].

| Escalation Signal Class | Detection Mechanism & Signal Extraction | Predictive Reliability on Code Failure | Latency & Computational Overhead | Operational Feasibility & Implementation Complexity |
| :---- | :---- | :---- | :---- | :---- |
| **Deterministic Verifier & Execution Feedback** | Exit codes from compilers, test harnesses (pytest), linters, and runtime exception traces[^6] | **Rank 1: Highest (Ground Truth)**. Direct empirical proof of task correctness; zero false-positive hallucination[^22] | Zero inference cost; bounded by local execution runtime[^22] | High feasibility; requires sandboxed container and test runner integration[^3] |
| **State Churn & AST Thrashing Metrics** | Algorithmic tracking of repetitive file edits, cyclic diff reversals, and duplicate tool calls[^11] | **Rank 2: High**. Repeating identical edits across $N \geq 2$ turns strongly indicates unrecoverable state traps[^4] | Negligible; computed via deterministic string matching or AST diffing | High feasibility; purely algorithmic tracking in the agent scaffold[^11] |
| **Learned Trajectory Monitors & Value Heads** | Auxiliary 8B model or value head scoring intermediate partial trajectories $T_{\leq K}$[^8] | **Rank 3: High**. Bypasses prompt-only Bayes floor by conditioning on empirical exploration traces[^8] | Minimal overhead; single forward pass of a local 8B model every $K$ steps[^15] | Moderate feasibility; requires offline training on trajectory rollouts[^8] |
| **Logprob Uncertainty & Token Entropy** | Mean token perplexity and sequence entropy calculated over generated patch spans[^41] | **Rank 4: Moderate**. Correlates with localized API unfamiliarity, but confounded by code boilerplate[^41] | Zero model generation cost; requires engine support for logprob emission[^41] | High feasibility if local inference server (e.g., vLLM, SGLang) exposes logprobs[^7] |
| **Self-Consistency & Multi-Sample Consensus** | Measuring divergence across $N$ independently sampled patches or test outputs[^18] | **Rank 5: Moderate to High**. High variance signals problem ambiguity, but shared blind spots pass undetected[^18] | Substantial cost; requires $N\times$ parallel generation and execution passes[^43] | Moderate feasibility; constrained by available local GPU compute capacity |
| **Self-Assessed Verbal Confidence** | Prompting the local model to score its own probability of success or explain its reasoning[^34] | **Rank 6: Negative Utility (Invalid)**. Severe overconfidence; models routinely validate hallucinated fixes[^11] | Low to moderate token overhead; high systemic failure rate[^37] | Trivial to prompt, but empirically destructive to system reliability[^34] |

Deterministic verifier outcomes represent the primary escalation signal in software engineering workflows[^6]. When an agent can write an execution-based reproducer that captures a bug, test execution yields a definitive binary signal[^3]. If a candidate patch fails this verification gate, the failure is unambiguous, bypassing the unreliability of model self-assessment[^6].  
When automated test suites are incomplete, state churn metrics provide the most effective heuristic indicator of failure[^4]. As established in multi-agent diagnostic evaluations, when an agent repeatedly alternates between two edits in the same file or issues duplicate search queries, it has exhausted its planning capability[^4]. Implementing an external circuit breaker that monitors file system diffs enables the system to intercept these loops and trigger frontier escalation before token context is wasted[^4].

## Comparative Analysis of Delegation Interfaces
The interface used to transfer tasks between the local orchestrator and the remote frontier model directly affects token efficiency, failure isolation, and financial cost[^2].

| Interface Paradigm | Delegation Mechanism | Token Efficiency & Information Density | Failure Isolation & Controllability | Frontier Prompt Caching Impact |
| :---- | :---- | :---- | :---- | :---- |
| **Free-Form Conversational Messages** | Unstructured conversational thread shared across models[^36] | **Low**. High conversational overhead, prose redundancy, and verbose descriptions[^36] | **Poor**. Vulnerable to prompt injection, instruction drift, and semantic ambiguity[^44] | **Severely Impaired**. Shifting conversational prefixes invalidate prompt caches[^2] |
| **Standard JSON-RPC Tool Calling** | Orchestrator invokes external models as function calls with defined argument schemas[^11] | **Moderate**. Structured syntax enforces parameter types, but tool transcripts expand rapidly[^13] | **Moderate**. Enforces boundaries but relies on local model schema compliance[^11] | **Moderate**. Static schema headers cache effectively, but argument history churns[^2] |
| **Full Session / Transcript Handoff** | Complete conversational transcript and workspace history transferred to frontier agent[^36] | **Lowest**. Transmits hundreds of thousands of historical tokens to expensive APIs[^2] | **Poor**. Propagates hallucinated context, dead ends, and erroneous hypotheses[^4] | **Worst**. Rapidly expanding contexts maximize frontier processing expenditures[^2] |
| **Structured Task Cards (JSON Envelope)** | Decoupled, schema-validated artifacts containing distilled context, diffs, and constraints[^6] | **Optimal**. Minimal token footprint containing only verified traces and target files[^3] | **High**. Prevents error propagation and enforces purpose-bound execution scopes[^44] | **Optimal**. Stable templated schemas maximize Anthropic prefix prompt cache hits[^2] |

Structured task cards represent the most robust delegation boundary for a local open-weight orchestrator[^6]. Transferring an entire raw conversational transcript to a frontier API is counterproductive: it forces the expensive model to ingest hundreds of thousands of historical tokens, transfers dead-end reasoning paths, and quickly eliminates the cost benefits of using a local model[^2].  
In contrast, structured task cards decouple problem exploration from patch authoring[^3]. By extracting only the essential problem description, the isolated failure trace, the reproduction script, and the target file diff, the task card encapsulates the task into a compact, self-contained payload[^3].  
This structure aligns directly with the prompt caching architectures of commercial APIs[^2]. In the Claude API, preserving an identical system prompt and schema prefix enables cached prompt reads at a fraction of standard input token costs[^2]. Modifying top-level system prompts or passing shifting conversational histories invalidates these caches, multiplying token costs by up to 25 to 50 times[^2]. A static, schema-validated task card preserves cache consistency while maintaining strict isolation between execution environments[^2].

### The Divergence of Effective Context from Advertised Windows
While modern models like Qwen 2.5 and Qwen 3 advertise context windows of 128K to 262K tokens via YaRN (Yet another RoPE) positional scaling, their Maximum Effective Context Window (MECW) in multi-step reasoning is substantially narrower[^38]. Quantitative context benchmarks demonstrate that models fall short of their advertised maximums, exhibiting sharp performance cliffs as sequence lengths expand[^40].  
For 30B-scale models, retrieval accuracy and constraint following decline past **32,768 tokens**[^38]. In multi-file repository navigation, open models exhibit pronounced "lost-in-the-middle" attention degradation, with retrieval accuracy dropping by 30% to 50% for information located in the central third of the context buffer[^39]. Consequently, an agent that ingests full source files into an unmanaged context quickly loses the ability to adhere to its initial instructions[^4].

### Operational Turn Boundaries
Empirical evaluations on SWE-bench Verified show that single-agent success rates for open models peak within early interaction rounds[^4]. Beyond **15 to 20 conversational turns**, unassisted models experience compounding planning errors[^4]. As failed bash executions and tool outputs accumulate, the model's autoregressive generation becomes biased by its own prior mistakes[^4]. Without external context pruning or trajectory rollback, the likelihood of resolving an issue past turn 20 approaches zero, with the agent consuming inference budget in unproductive loops[^4]. Context compaction studies confirm that actively pruning session history to under 49K tokens raises resolve rates on extended sessions from 41% to 53% (+12.3 percentage points), underscoring that context unrolling degrades agent reliability[^5].

### File Modification Breadth Limits
Local 30B models operate reliably when identifying and modifying **1 to 3 localized source files**[^49]. When a software issue requires coordinating changes across **4 or more files**—as observed in SWE-bench ProMax, where tasks average 11.4 modified files and 261 lines of code—the performance of sub-frontier models drops significantly[^49]. The model struggle to track dependencies, import paths, and interface contracts across multiple modules simultaneously, leading to cross-file regressions[^4]. Tasks that touch four or more files exceed the autonomous capacity of local 30B models and represent an explicit escalation boundary[^49].

## Architectural and System Design Recommendations for a Prompted Qwen Orchestrator
To deploy a local Qwen 3.x-class model (~30B parameters, running on a single GPU) to orchestrate an agentic coding workflow that delegates to Claude APIs without a human in the loop, the system must be constructed as a **deterministic, externally governed state machine**[^6]. The local model should execute operational tasks within strict verification boundaries, while an external Python harness enforces all escalation decisions[^6].

### Deterministic State Machine Architecture
The control flow must be governed by an external Python orchestration layer rather than the local LLM's open-ended reasoning[^11]. The workflow should progress through three sequential, non-recurrent execution phases:  
The exploration and localization phase restricts the local Qwen model to read-only shell tools (specifically grep, find, and file inspection with line-number boundaries)[^3]. The model is tasked with locating the relevant source files and generating a reproduction script (reproduce_issue.py)[^3].  
The reproduction and verification phase executes the reproduction script in an isolated container[^3]. The environment must verify that the script fails on the unmodified codebase with the exact error described in the issue, establishing an objective ground truth for subsequent patch validation[^3].  
The patch authoring and testing phase allows the local Qwen model up to two attempts to draft a patch and run the reproduction test[^6]. If the reproduction script and the project unit test suite pass with returncode zero, the patch is committed and the session completes without invoking external APIs[^4].

### Deterministic Escalation Gates
The Python execution scaffold must monitor the interaction trace and trigger immediate escalation to the Claude API upon detecting any of the following four conditions:  
A reproduction stall occurs if the local model completes 8 conversational turns without identifying candidate source files or authoring a failing reproducer script[^8].  
A verification failure loop occurs if the local model's candidate patch fails the reproduction test or existing regression tests on two consecutive attempts[^4].  
State churn is triggered if the local model modifies the same source file three times within four turns or issues duplicate bash inspection commands, indicating an unrecoverable planning loop[^4].  
A file breadth threshold is met if the localization step identifies that resolving the issue requires modifying four or more source files[^49].

### Structured Task Card Protocol
When an escalation gate is triggered, the execution harness halts the local model, extracts the verified artifacts, and synthesizes a Structured Task Card formatted as an immutable JSON payload[^6]:

JSON  
{  
  "task_metadata": {  
    "issue_id": "BUG-8492",  
    "target_repository": "django/django",  
    "affected_files": \["django/db/models/query.py"\]  
  },  
  "context": {  
    "problem_statement": "QuerySet.aggregate() crashes with TypeError when combining distinct and expressions.",  
    "reproduction_script": "import pytest\\nfrom django.db import models...",  
    "execution_trace": "TypeError: 'CombinedExpression' object is not iterable at django/db/models/query.py:382",  
    "local_candidate_diff": "--- a/django/db/models/query.py\\n+++ b/django/db/models/query.py\\n@@ -382,2 +382,2 @@..."  
  },  
  "escalation_reason": "VERIFICATION_FAILURE_LOOP",  
  "delegation_role": "PATCH_AUTHORING",  
  "instructions": "Analyze the problem statement, execution trace, and candidate diff. Generate a complete, minimal patch resolving the failure without side effects. Return output strictly in unified diff format enclosed within \`\`\`diff code blocks."  
}

This structured envelope ensures that the frontier model receives only relevant, filtered context[^3]. It prevents token bloat and insulates the frontier model from any reasoning errors present in the local model's conversational history[^4].

### Model Tier Dispatch Policy
The system should route task cards across the Claude model family based on the specific operational bottleneck[^2]:  
Claude Haiku should be selected for localized syntax fixes, compiler error repair, regular expression generation, and test script formatting[^2].  
Claude Sonnet should serve as the default escalation engine for single-module algorithmic debugging, logic fixes, and standard unit-test repair[^2].  
Claude Opus should be reserved exclusively for multi-file architectural refactors, broad interface redesigns, or cases where a patch authored by Claude Sonnet fails verification[^2]. In production systems, Opus invocations should account for less than 5% to 10% of total interactions to preserve cost efficiency[^3].

### Context Compaction and Cache Hygiene
To maintain local Qwen performance and minimize commercial API charges, the system must enforce strict context management policies[^2]:  
The active working context of the local Qwen model must be capped at 32,768 tokens[^38]. Every 4 turns, the harness should run an automated compaction step that truncates terminal stdout logs to the last 40 lines, eliminates redundant file reads, and preserves only the original issue text, active diffs, and current test results[^2].  
System prompt prefixes must remain static across all model calls to maximize KV-cache reuse on local inference engines (such as vLLM or SGLang) and optimize prompt caching on the Anthropic API, ensuring fast inference and reducing token expenditures[^2].  
By structuring the workflow around a deterministic execution scaffold, using objective verifier feedback as the primary escalation trigger, and communicating via isolated task cards, this hybrid architecture matches the task success rates of end-to-end frontier agents while capturing the 60% to 70% cost savings demonstrated across current multi-agent systems research[^1].
